==================================================

==================================================
4. SECURITY OBJECTIVE
==================================================

The future system should be designed so that:

1. Audio/video media is protected end-to-end between the two participants.

2. The signaling infrastructure cannot access usable audio/video media.

3. The TURN server is treated as a relay and not as a trusted media decryption endpoint.

4. Private cryptographic identity material remains on the user's device.

5. The backend has as little information as technically practical.

6. Temporary call state is ephemeral.

7. Call history is not intentionally persisted.

8. Audio/video recordings are not intentionally created.

9. No analytics or tracking system exists.

10. Third-party dependencies are minimized.

11. Security-sensitive cryptography uses established, reviewed primitives.

12. Browser storage and browser caching are treated as privacy-sensitive.

13. Logs are designed to avoid unnecessary sensitive information.

14. Pairing eventually authenticates the intended partner device.

15. Cryptographic identity changes can eventually be detected.

16. Security failures should fail safely rather than silently downgrade security.

17. The architecture must clearly document limitations instead of making impossible security promises.

LOCAL-FIRST SENSITIVE STATE

MINIMAL INFRASTRUCTURE TRUST

- approved dependencies
- prohibited data
- planned future browser APIs

If a security requirement conflicts with an existing implementation:

STOP, document the conflict, and choose the safer design.

Do not silently weaken an existing requirement.

3. CONTENT SECURITY POLICY
============================================================

Implement a strict Content Security Policy.

The goal is to minimize:

- XSS
- injected scripts
- unauthorized external resources
- malicious third-party code
- unexpected network connections
- unsafe embedded content

Start from the principle:

DEFAULT DENY.

Use the narrowest policy compatible with the actual application.

Evaluate directives including:

default-src
script-src
style-src
img-src
font-src
connect-src
media-src
object-src
base-uri
form-action
frame-ancestors
worker-src
manifest-src
upgrade-insecure-requests

Do not add:

*
https:

'unsafe-inline'
'unsafe-eval'

unless there is a documented technical requirement.

If Next.js requires a specific exception, determine exactly why it is
needed and document it.

Do NOT weaken the CSP simply because a development feature breaks.

Distinguish development requirements from production requirements.

4. CSP AND FUTURE WEBRTC
============================================================

The application will eventually use:

- WebRTC
- WebSocket signaling
- TURN
- STUN
- microphone
- camera

Do NOT configure actual WebRTC endpoints yet.

However, document how CSP will eventually need to accommodate
authorized signaling/network endpoints.

Do NOT use broad:

ONLY APPROVED ENDPOINTS.

The final endpoint list will be introduced when signaling and TURN are
implemented.

Do not invent production endpoints.


============================================================
5. CSP REPORTING
============================================================

Evaluate CSP reporting.

Do NOT automatically introduce a third-party CSP reporting service.

Because Between Us follows a privacy-first architecture, determine
whether CSP reporting itself creates unnecessary metadata.

Document:

- whether CSP reporting is enabled
- what data reports could contain
- who would receive reports
- privacy implications
- whether local/self-hosted reporting is preferable
- whether reporting is disabled in production

Do not introduce analytics under the name of CSP reporting.


============================================================
6. FRAME PROTECTION
============================================================

Prevent unauthorized framing of the application.

Configure:

frame-ancestors 'none'

unless a legitimate architectural requirement exists.

Evaluate:

X-Frame-Options

and document compatibility considerations.

The application should not be embeddable by arbitrary third-party
websites.


============================================================
7. MIME SNIFFING PROTECTION
============================================================

Configure:

X-Content-Type-Options: nosniff

Document why MIME sniffing protection matters.

Ensure static resources are served with correct content types.


============================================================
8. REFERRER POLICY
============================================================

Use a privacy-preserving Referrer-Policy.

Evaluate:

no-referrer

or another appropriately restrictive policy.

Prefer the option that minimizes unnecessary URL/referrer leakage.

Document the choice.

The application should not unnecessarily disclose sensitive navigation
information to other origins.


============================================================
9. PERMISSIONS POLICY
============================================================

Create a restrictive Permissions-Policy.

Future sensitive browser capabilities include:

- microphone
- camera

Do not grant these capabilities to arbitrary frames or origins.

Design the policy so that microphone/camera access is limited to the
application's own origin where possible.

Do not grant unnecessary permissions such as:

- geolocation
- payment
- USB
- Bluetooth
- serial
- accelerometer
- gyroscope
- clipboard-read

unless a future approved architecture requires them.

For now, do not implement microphone/camera functionality.

Document the intended future policy.


============================================================
10. CAMERA AND MICROPHONE PRIVACY
============================================================

Do not request microphone or camera permissions in Phase 05.

Do not call:

navigator.mediaDevices.getUserMedia()

yet.

Instead establish the security requirements for Phase 13 and Phase 14.

Document:

- permission must be explicitly requested
- permissions must be requested only when needed
- camera/microphone must not activate automatically
- streams must be stopped after the call
- UI must clearly indicate active media capture
- permission failures must fail safely
- no captured media should be persisted
- no captured media should be logged

These requirements must become prerequisites for future audio/video
implementation.
